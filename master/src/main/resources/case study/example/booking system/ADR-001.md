# ADR-001: انتخاب Elasticsearch برای جست‌وجوی کاتالوگ سفر

## Status

Accepted

## Date

2026-10-02

## Context and Problem

سیستم رزرو باید امکان جست‌وجوی سریع اطلاعات تعداد زیادی از خدمات سفر مانند هتل‌ها، پروازها و سایر خدمات گردشگری را فراهم کند.

کاربر ممکن است بر اساس معیارهایی مانند:

* نام هتل یا سرویس
* مقصد و موقعیت جغرافیایی
* امکانات هتل
* نوع سرویس
* فیلترها و معیارهای مختلف جست‌وجو

اقدام به جست‌وجو کند.

از طرف دیگر، همه اطلاعات یک سرویس سفر ماهیت یکسانی ندارند. اطلاعات نسبتاً ثابت مانند نام، توضیحات، امکانات و موقعیت مکانی را می‌توان در سیستم به‌صورت محلی نگهداری کرد، اما اطلاعات حساس و لحظه‌ای مانند:

* موجودی اتاق یا صندلی
* قیمت فعلی
* وضعیت رزرو
* قیمت نهایی قابل پرداخت

باید از Provider مربوطه دریافت و قبل از رزرو مجدداً اعتبارسنجی شوند.

دو رویکرد اصلی برای جست‌وجوی اطلاعات وجود دارد:

1. ارسال هر Search به Providerهای خارجی
2. ذخیره اطلاعات در یک پایگاه داده محلی و انجام Search روی آن

ارسال تمام درخواست‌های Search به Providerهای خارجی می‌تواند باعث افزایش latency، وابستگی بیشتر به در دسترس بودن Providerها، افزایش تعداد درخواست‌ها و محدودیت‌های احتمالی API Providerها شود.

از طرف دیگر، استفاده از PostgreSQL به‌عنوان تنها محل جست‌وجوی کاتالوگ، اگرچه امکان جست‌وجوی متنی و فیلتر کردن را فراهم می‌کند، برای workload اصلی و گسترده‌ی Search سیستم، قابلیت‌های تخصصی موتورهای Search مانند Full-Text Search، Filtering و Faceting را به‌صورت تخصصی ارائه نمی‌دهد.

بنابراین نیاز است یک راهکار برای نگهداری و جست‌وجوی سریع اطلاعات نسبتاً ثابت کاتالوگ در نظر گرفته شود، بدون اینکه اطلاعات لحظه‌ای Provider به‌عنوان Source of Truth در آن ذخیره شود.

---

## Options Considered

### Option 1: جست‌وجوی مستقیم در Providerهای خارجی

در این روش، هر درخواست Search مستقیماً به Providerهای مربوطه ارسال می‌شود.

#### Advantages

* اطلاعات مستقیماً از Provider دریافت می‌شود.
* نیازی به نگهداری Catalog محلی نیست.
* مشکل Synchronization برای اطلاعات Catalog کاهش پیدا می‌کند.

#### Disadvantages

* افزایش latency در Search
* وابستگی Search به availability Providerهای خارجی
* افزایش تعداد درخواست‌ها به Providerها
* احتمال برخورد با Rate Limit
* کاهش کنترل روی قابلیت‌های Search و Filtering
* افزایش بار روی APIهای خارجی

---

### Option 2: ذخیره Catalog در PostgreSQL و جست‌وجو روی آن

در این روش، اطلاعات Catalog در PostgreSQL ذخیره شده و Search روی داده‌های relational انجام می‌شود.

#### Advantages

* استفاده از یک پایگاه داده موجود
* سادگی نسبی معماری
* امکان استفاده از SQL و Indexهای relational
* امکان نگهداری داده‌های Catalog به‌صورت ساختاریافته

#### Disadvantages

* Search workload از workload مربوط به Transactionهای Booking جدا نیست.
* پیاده‌سازی Searchهای پیچیده‌تر می‌تواند پیچیدگی Queryها و Indexها را افزایش دهد.
* قابلیت‌های تخصصی Search مانند Full-Text Search، Filtering و Faceting در Elasticsearch به‌صورت تخصصی‌تری ارائه می‌شوند.
* با افزایش حجم و پیچیدگی Search، ممکن است نیاز به معماری جداگانه برای Search ایجاد شود.

---

### Option 3: استفاده از Elasticsearch برای Catalog و Provider برای اطلاعات لحظه‌ای

در این روش، اطلاعات نسبتاً ثابت Catalog در Elasticsearch ذخیره می‌شوند و Elasticsearch به‌عنوان Search Index استفاده می‌شود.

اطلاعاتی مانند:

* نام
* توضیحات
* موقعیت
* امکانات
* نوع سرویس

در Elasticsearch نگهداری می‌شوند.

اما اطلاعات لحظه‌ای مانند Availability و Price در Elasticsearch به‌عنوان Source of Truth ذخیره نمی‌شوند و هنگام نیاز از Provider خارجی دریافت و اعتبارسنجی می‌شوند.

#### Advantages

* Search سریع و قابل توسعه
* مناسب برای Full-Text Search
* پشتیبانی مناسب از Filtering و Faceting
* کاهش تعداد درخواست‌های Search به Providerهای خارجی
* جدا شدن Search workload از Transactionهای Booking
* حفظ اطلاعات لحظه‌ای در Provider به‌عنوان Source of Truth
* امکان به‌روزرسانی Catalog از طریق Webhook/Event APIهای Provider

#### Disadvantages

* اضافه شدن Elasticsearch به معماری و افزایش operational complexity
* اطلاعات Catalog ممکن است برای مدت کوتاهی با Provider اختلاف داشته باشد.
* نیاز به فرآیند Synchronization و Indexing
* نیاز به مدیریت Availability و Health مربوط به Elasticsearch

---

## Decision

گزینه سوم انتخاب می‌شود.

سیستم از **Elasticsearch به‌عنوان Search Index برای اطلاعات نسبتاً ثابت کاتالوگ سفر** استفاده می‌کند.

اطلاعاتی مانند مشخصات هتل، امکانات، توضیحات و موقعیت در Elasticsearch نگهداری می‌شوند و Search Service درخواست‌های جست‌وجو را روی Elasticsearch اجرا می‌کند.

اطلاعات لحظه‌ای و حساس مانند Availability، قیمت فعلی و وضعیت نهایی رزرو در Elasticsearch به‌عنوان Source of Truth نگهداری نمی‌شوند.

هنگامی که کاربر یک سرویس را برای مشاهده جزئیات نهایی یا رزرو انتخاب می‌کند، Booking Service از طریق Travel Integration Service اطلاعات فعلی را از Provider دریافت کرده و Availability و Price را مجدداً اعتبارسنجی می‌کند.

به‌روزرسانی اطلاعات Catalog نیز از طریق Webhook/Event APIهای Provider دریافت شده و توسط Travel Integration Service در Elasticsearch اعمال می‌شود.

به این ترتیب Elasticsearch مسئول **Search و Catalog Read Model** است و Provider خارجی مسئول **اطلاعات Real-Time و نهایی رزرو** باقی می‌ماند.

---

## Consequences

### Positive Consequences

* Search با latency پایین‌تر و قابلیت توسعه بیشتر انجام می‌شود.
* تعداد درخواست‌های غیرضروری به Providerهای خارجی کاهش پیدا می‌کند.
* Search از Transactionهای Booking جدا می‌شود.
* Availability و Price از منبع اصلی خود دریافت و قبل از رزرو اعتبارسنجی می‌شوند.
* امکان پیاده‌سازی Searchهای پیچیده، Filtering و Faceting فراهم می‌شود.
* تغییرات Catalog می‌توانند بدون وابستگی مستقیم Search به Provider، از طریق Webhook در Index اعمال شوند.

### Negative Consequences

* Elasticsearch یک جزء جدید در زیرساخت سیستم خواهد بود.
* نیاز به مدیریت Index و Synchronization وجود دارد.
* Catalog ممکن است برای مدت کوتاهی با اطلاعات Provider متفاوت باشد.
* در صورت unavailable بودن Elasticsearch، قابلیت Search Catalog تحت تأثیر قرار می‌گیرد و باید برای Recovery آن برنامه‌ریزی شود.
* Availability و Price همچنان به availability سرویس‌های Provider وابسته هستند.

## Implementation

معماری به‌صورت زیر پیاده‌سازی می‌شود:

```text
Customer
   |
   v
Search Service
   |
   v
Elasticsearch
   |
   |  Static Catalog Information
   |
   v
Search Results


Customer
   |
   v
Booking Service
   |
   v
Travel Integration Service
   |
   v
External Travel Provider
   |
   +--> Current Availability
   |
   +--> Current Price
   |
   +--> Final Booking
```

برای به‌روزرسانی Catalog:

```text
External Travel Provider
          |
          | Webhook / Event API
          v
Travel Integration Service
          |
          v
Elasticsearch
```

### Data Ownership

| Data                    | Source of Truth              |
| ----------------------- | ---------------------------- |
| Hotel name              | Travel Provider              |
| Hotel description       | Travel Provider              |
| Hotel facilities        | Travel Provider              |
| Location                | Travel Provider              |
| Current availability    | External Travel Provider     |
| Current price           | External Travel Provider     |
| Booking status          | Booking Service / PostgreSQL |
| Final booking reference | Booking Service / PostgreSQL |
| Search index            | Elasticsearch                |

Elasticsearch در این معماری **Source of Truth برای اطلاعات Business نیست** و به‌عنوان Search Index / Read Model مورد استفاده قرار می‌گیرد.

## Monitoring / Review

برای بررسی صحت این تصمیم، موارد زیر باید در Production مانیتور شوند:

* Search latency، به‌خصوص `p95` و `p99`
* Elasticsearch availability
* Elasticsearch query errors
* Indexing failures
* تعداد و زمان به‌روزرسانی Catalog
* اختلاف یا تأخیر احتمالی بین Catalog و Provider
* تعداد درخواست‌های Search به Provider
* Provider API latency و error rate
* نرخ شکست دریافت Availability و Price

در صورت افزایش قابل توجه حجم Catalog، پیچیدگی Search، تعداد Providerها یا نیاز به پردازش Eventهای با حجم بالا، این تصمیم باید مجدداً بررسی شود.

در صورت ایجاد نیاز واقعی به Event Streaming یا پردازش asynchronous با حجم بالا، استفاده از Message Broker می‌تواند در یک ADR جداگانه بررسی شود.
