# ADR-001: انتخاب Elasticsearch برای جست‌وجوی کاتالوگ سفر

### عنوان: انتخاب Elasticsearch برای جست‌وجوی کاتالوگ خدمات سفر

### وضعیت: پذیرفته شده

### تاریخ: ۱۴۰۵/۰۷/۱۰

### زمینه و مسئله:

سیستم رزرو ما نیاز به جست‌وجوی سریع و مقیاس‌پذیر در حجم زیادی از اطلاعات مربوط به خدمات سفر مانند هتل‌ها، پروازها و سایر خدمات گردشگری دارد.

کاربران باید بتوانند بر اساس معیارهایی مانند نام، مقصد، موقعیت جغرافیایی، امکانات و سایر فیلترها خدمات موردنظر خود را جست‌وجو کنند.

از طرفی، همه اطلاعات خدمات سفر ماهیت یکسانی ندارند. اطلاعات نسبتاً ثابت مانند نام، توضیحات، امکانات و موقعیت مکانی می‌توانند به‌صورت محلی ذخیره شوند، اما اطلاعات لحظه‌ای و حساس مانند موجودی، قیمت فعلی و وضعیت رزرو باید از Provider خارجی دریافت و قبل از رزرو مجدداً اعتبارسنجی شوند.

ارسال تمام درخواست‌های جست‌وجو به Providerهای خارجی باعث افزایش وابستگی سیستم، latency و تعداد درخواست‌های خارجی می‌شود. همچنین استفاده از PostgreSQL به‌عنوان تنها موتور جست‌وجو، با توجه به حجم و پیچیدگی عملیات Search، انتخاب مناسبی برای workload اصلی جست‌وجو نیست.

بنابراین نیاز به یک Search Engine مستقل برای نگهداری و جست‌وجوی سریع اطلاعات نسبتاً ثابت کاتالوگ وجود دارد.

### گزینه‌های بررسی شده:

۱. جست‌وجوی مستقیم در Providerهای خارجی

* مزایا: دریافت مستقیم اطلاعات از Provider، عدم نیاز به نگهداری Catalog محلی

* معایب: افزایش latency، وابستگی Search به availability Provider، افزایش تعداد درخواست‌ها، احتمال Rate Limit و محدودیت در قابلیت‌های جست‌وجو

۲. ذخیره اطلاعات Catalog در PostgreSQL و جست‌وجو روی آن

* مزایا: معماری ساده‌تر، استفاده از پایگاه داده موجود، امکان استفاده از SQL و Indexها

* معایب: جدا نبودن workload جست‌وجو از تراکنش‌های اصلی، پیچیدگی بیشتر در Searchهای پیشرفته و نداشتن قابلیت‌های تخصصی Search در سطح Elasticsearch

۳. استفاده از Elasticsearch برای Catalog و Provider برای اطلاعات لحظه‌ای

* مزایا: جست‌وجوی سریع، پشتیبانی از Full-Text Search و Filtering، کاهش درخواست‌های غیرضروری به Providerها، جداسازی workload جست‌وجو از Booking

* معایب: افزایش پیچیدگی زیرساخت، نیاز به Synchronization و Indexing و احتمال وجود اختلاف موقت بین Catalog و اطلاعات Provider

### تصمیم:

استفاده از **Elasticsearch به‌عنوان Search Engine و Index برای اطلاعات نسبتاً ثابت کاتالوگ خدمات سفر** انتخاب می‌شود.

اطلاعاتی مانند نام، توضیحات، امکانات، نوع سرویس و موقعیت مکانی در Elasticsearch ذخیره می‌شوند و Search Service برای جست‌وجوی این اطلاعات از Elasticsearch استفاده می‌کند.

اطلاعات لحظه‌ای مانند Availability، قیمت فعلی و وضعیت نهایی رزرو در Elasticsearch به‌عنوان Source of Truth ذخیره نمی‌شوند.

هنگام انتخاب یک سرویس توسط کاربر، Booking Service از طریق Travel Integration Service اطلاعات فعلی را از Provider دریافت کرده و Availability و Price را مجدداً اعتبارسنجی می‌کند.

به‌روزرسانی اطلاعات Catalog نیز از طریق Webhook یا Event APIهای Provider دریافت شده و توسط Travel Integration Service در Elasticsearch اعمال خواهد شد.

### پیامدها:

* سرعت و قابلیت توسعه Search افزایش پیدا می‌کند.

* تعداد درخواست‌های غیرضروری به Providerهای خارجی کاهش پیدا می‌کند.

* workload مربوط به Search از تراکنش‌های Booking جدا می‌شود.

* اطلاعات لحظه‌ای همچنان از Provider به‌عنوان Source of Truth دریافت می‌شوند.

* سیستم به یک مؤلفه زیرساختی جدید یعنی Elasticsearch وابسته می‌شود.

* نیاز به مدیریت Index و Synchronization بین Catalog و Provider ایجاد می‌شود.

* در صورت در دسترس نبودن Elasticsearch، قابلیت جست‌وجوی Catalog تحت تأثیر قرار خواهد گرفت.

### پیاده‌سازی:

۱. ایجاد Elasticsearch به‌عنوان Search Engine سیستم

۲. ایجاد Indexهای مناسب برای اطلاعات Catalog خدمات سفر

۳. پیاده‌سازی Search Service برای انجام جست‌وجو و Filtering روی Elasticsearch

۴. پیاده‌سازی Travel Integration Service برای ارتباط با Providerهای خارجی

۵. دریافت تغییرات Catalog از طریق Webhook یا Event API و به‌روزرسانی Elasticsearch

۶. دریافت Availability و Price فعلی از Provider هنگام انتخاب و رزرو سرویس

۷. عدم استفاده از Elasticsearch به‌عنوان Source of Truth برای اطلاعات لحظه‌ای و تراکنش‌های Booking

### وضعیت نظارت:

این تصمیم به‌صورت دوره‌ای بازبینی خواهد شد تا از تطابق معماری Search با نیازهای در حال رشد سیستم اطمینان حاصل شود.

معیارهای کلیدی برای ارزیابی شامل زمان پاسخ‌گویی Search، نرخ خطای Elasticsearch، وضعیت Indexing، تأخیر Synchronization با Providerها، تعداد درخواست‌های ارسال‌شده به Providerها و میزان استفاده از منابع Elasticsearch خواهد بود.
