# ADR-003: استفاده از External SSO برای احراز هویت

### عنوان: استفاده از External SSO Provider برای احراز هویت کاربران

### وضعیت: پذیرفته شده

### تاریخ: ۱۴۰۵/۰۷/۱۰

### زمینه و مسئله:

سیستم رزرو نیاز به احراز هویت امن کاربران دارد و کاربران می‌توانند از کشورهای مختلف و با پلتفرم‌های مختلف به سیستم دسترسی داشته باشند.

پیاده‌سازی احراز هویت به‌صورت داخلی نیازمند مدیریت مواردی مانند Login، مدیریت Session یا Token، نگهداری اطلاعات هویتی و امنیت Credentialها است.

از طرف دیگر، شرکت می‌تواند از یک سرویس SSO خارجی برای مدیریت هویت کاربران استفاده کند. در این حالت سیستم رزرو مسئولیت احراز هویت مستقیم کاربران را بر عهده نمی‌گیرد و از استانداردهای OAuth 2.0 و OpenID Connect برای تعامل با Identity Provider استفاده می‌کند.

همچنین Authorization مربوط به دسترسی‌های Business نباید صرفاً توسط SSO انجام شود و باید در لایه‌های داخلی سیستم نیز کنترل شود.

### گزینه‌های بررسی شده:

۱. پیاده‌سازی Authentication به‌صورت داخلی در سیستم

* مزایا: کنترل کامل روی فرآیند احراز هویت، عدم وابستگی به Provider خارجی

* معایب: افزایش پیچیدگی، نیاز به نگهداری Credentialها، مسئولیت بیشتر در زمینه امنیت Authentication و نیاز به توسعه و نگهداری مکانیزم‌های مربوط به Token و Session

۲. استفاده از External SSO Provider

* مزایا: استفاده از راهکار تخصصی مدیریت هویت، کاهش مسئولیت سیستم در مدیریت Credentialها، استفاده از استانداردهای OAuth 2.0 و OpenID Connect و امکان استفاده از یک Identity Provider مشترک برای چند سیستم

* معایب: وابستگی به SSO Provider، نیاز به مدیریت Token و خطاهای ارتباط با Provider

### تصمیم:

استفاده از **External SSO Provider** برای Authentication کاربران انتخاب می‌شود.

سیستم از **OpenID Connect بر بستر OAuth 2.0** برای احراز هویت و دریافت اطلاعات هویتی کاربران استفاده خواهد کرد.

API Gateway به‌عنوان نقطه ورود سیستم، Token دریافت‌شده از SSO Provider را اعتبارسنجی کرده و درخواست را به سرویس مربوطه ارسال می‌کند.

Authorization در دو سطح انجام می‌شود:

* API Gateway برای کنترل دسترسی‌های عمومی و سطح API
* سرویس مربوطه برای کنترل دسترسی‌های Business و Fine-Grained Authorization

به‌عنوان مثال، Gateway می‌تواند بررسی کند که کاربر دارای Token معتبر و Permission لازم برای دسترسی به یک API است، در حالی که Booking Service بررسی می‌کند آیا کاربر مجاز به مشاهده یا تغییر Booking موردنظر است یا خیر.

در این معماری، **Auth Service مستقل داخلی ایجاد نمی‌شود** و SSO Provider به‌عنوان Identity Provider خارجی مورد استفاده قرار می‌گیرد.

### پیامدها:

* مسئولیت مدیریت Credentialهای کاربران از سیستم رزرو خارج می‌شود.

* سیستم از استانداردهای رایج OAuth 2.0 و OpenID Connect استفاده می‌کند.

* نیاز به پیاده‌سازی و مدیریت ارتباط با SSO Provider وجود خواهد داشت.

* در دسترس بودن SSO Provider می‌تواند روی فرآیند Authentication تأثیر بگذارد.

* Authorization مربوط به Business همچنان باید در سرویس‌های داخلی پیاده‌سازی و کنترل شود.

* معماری سیستم ساده‌تر می‌شود و نیازی به ایجاد و نگهداری یک Auth Service مستقل وجود ندارد.

### پیاده‌سازی:

۱. اتصال API Gateway به External SSO Provider

۲. استفاده از OpenID Connect برای Authentication کاربران

۳. دریافت و اعتبارسنجی Access Token / ID Token مطابق با قرارداد SSO Provider

۴. استخراج اطلاعات هویتی و Claims موردنیاز از Token

۵. اعمال کنترل دسترسی سطح API در API Gateway

۶. پیاده‌سازی Fine-Grained Authorization در سرویس‌های Business مانند Booking Service

۷. عدم نگهداری Password کاربران در سیستم رزرو

۸. استفاده از Redis در Gateway برای داده‌های موقتی موردنیاز مانند Token/Authorization Cache در صورت نیاز

### وضعیت نظارت:

این تصمیم به‌صورت دوره‌ای بازبینی خواهد شد و معیارهای زیر برای بررسی آن مورد توجه قرار می‌گیرند:

* نرخ خطاهای Authentication
* latency مربوط به SSO Provider
* availability و downtime سرویس SSO
* نرخ خطا و انقضای Tokenها
* خطاهای Authorization
* تعداد درخواست‌های ناموفق به دلیل مشکلات SSO

در صورت تغییر نیازهای امنیتی، افزایش تعداد سیستم‌های وابسته به Identity Provider یا ایجاد نیاز به قابلیت‌های جدید در مدیریت هویت، این تصمیم مجدداً بررسی خواهد شد.
