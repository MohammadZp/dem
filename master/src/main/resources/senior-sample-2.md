# سؤال ۵

سؤال: در یک پروژه توزیع‌شده، چگونه می‌توان با استفاده از ابزارهای مانیتورینگ، خطاهای غیرمنتظره را ردیابی و تحلیل کرد؟

راهنما: ردیابی خطاها در پروژه‌های توزیع‌شده نیازمند ابزارهای مناسب و استراتژی درست است.

سطح: Senior

### پاسخ

در سیستم‌های توزیع‌شده، یک درخواست ممکن است از چند سرویس عبور کند؛ بنابراین پیدا کردن منشأ خطا فقط با بررسی Logهای یک سرویس کافی نیست. باید از ترکیب `Logs`، `Metrics` و `Distributed Tracing` استفاده کنیم.

۱. متمرکزسازی Logs

Logهای سرویس‌ها باید در یک سامانه مرکزی مانند ELK Stack یا OpenSearch جمع‌آوری شوند. هر Log بهتر است اطلاعاتی مانند زمان، نام سرویس، سطح خطا، شناسه درخواست و جزئیات Exception را داشته باشد.

۲. استفاده از Correlation ID و Trace ID

برای دنبال کردن یک درخواست بین سرویس‌ها، از شناسه‌های مشترک استفاده می‌کنیم:

- `Correlation ID`: ارتباط دادن Logهای مربوط به یک درخواست یا جریان کاری.
- `Trace ID`: شناسایی یک Trace کامل که شامل چندین Span در سرویس‌های مختلف است.
- `Span ID`: شناسایی یک بخش از عملیات درون Trace.

این شناسه‌ها کمک می‌کنند مسیر درخواست و محل وقوع خطا را سریع‌تر پیدا کنیم.

۳. استفاده از Distributed Tracing

ابزارهایی مانند `OpenTelemetry` برای Instrumentation و ابزارهایی مانند Jaeger یا Grafana Tempo برای مشاهده Traceها کاربرد دارند. با بررسی Trace می‌توان متوجه شد که کدام سرویس یا فراخوانی خارجی باعث افزایش Latency یا شکست درخواست شده است.

۴. بررسی Metrics و Alerting

با ابزارهایی مانند Prometheus و Grafana می‌توان نرخ خطا، Latency، مصرف CPU و Memory و تعداد درخواست‌ها را بررسی کرد. برای شاخص‌هایی مانند افزایش `Error Rate` یا `p99 Latency` باید Alert تعریف شود تا مشکل پیش از گسترش شناسایی شود.

۵. تحلیل ریشه‌ای خطا (Root Cause Analysis)

پس از مشاهده خطا، باید موارد زیر بررسی شوند:

- آیا خطا از سرویس اصلی است یا از یک Dependency خارجی؟
- آیا خطا بعد از تغییر نسخه یا Deployment جدید شروع شده است؟
- آیا Timeout، Connection Pool Exhaustion یا Network Failure رخ داده است؟
- آیا Retry باعث افزایش بار و گسترش خطا شده است؟
- آیا یک خطا در چند سرویس زنجیره‌ای منتشر شده است؟

همچنین باید از ثبت اطلاعات حساس مانند Password، Token و اطلاعات شخصی در Logها خودداری کرد.

نتیجه:

برای تحلیل خطاهای سیستم توزیع‌شده، Logs متمرکز، Metrics، Distributed Tracing و شناسه‌های مشترک مانند Trace ID را ترکیب می‌کنیم. سپس با بررسی مسیر درخواست، وابستگی‌ها و تغییرات اخیر، علت اصلی خطا را شناسایی می‌کنیم

# سؤال ۷

سؤال: در طراحی یک سیستم مقیاس‌پذیر جاوا، چه معماری‌هایی برای افزایش Availability و Fault Tolerance پیشنهاد می‌شود؟

راهنما: مقیاس‌پذیری و تحمل خطا از چالش‌های اساسی سیستم‌های بزرگ هستند.

سطح: Senior

### پاسخ

برای افزایش `Availability` و `Fault Tolerance` باید سیستم را طوری طراحی کنیم که با خرابی یک Instance، سرویس خارجی یا بخشی از زیرساخت، کل سیستم از دسترس خارج نشود.

مهم‌ترین راهکارها عبارت‌اند از:

- High Availability: اجرای چند Instance از سرویس در سرورها یا Availability Zoneهای متفاوت و استفاده از `Load Balancer` برای توزیع درخواست‌ها.
- Horizontal Scaling: اضافه کردن Instanceهای جدید به‌جای افزایش منابع یک سرور؛ به‌خصوص برای سرویس‌های Stateless.
- Redundancy: جلوگیری از وجود Single Point of Failure در اجزایی مانند Database، Message Broker و شبکه.
- Circuit Breaker: جلوگیری از فراخوانی مکرر یک Dependency معیوب و کاهش انتشار خطا بین سرویس‌ها.
- Timeout و Retry: تعیین Timeout مناسب و استفاده از Retry محدود همراه با Exponential Backoff و Jitter. Retry باید برای عملیات مناسب و ترجیحاً Idempotent انجام شود.
- Bulkhead: جداسازی منابع سرویس‌ها یا عملیات‌ها، مانند Thread Poolها، تا اشکال در یک بخش منابع سایر بخش‌ها را مصرف نکند.
- Health Check: تشخیص وضعیت Instanceها برای جلوگیری از ارسال درخواست به نمونه‌های ناسالم.
- Database Resilience: استفاده از Replication، Backup و Recovery و در صورت نیاز Failover. Replication به‌تنهایی جایگزین Backup نیست.
- Graceful Degradation: در صورت خرابی یک قابلیت غیرضروری، ارائه سرویس با امکانات محدود به‌جای از کار افتادن کل سیستم.

همچنین باید `Metrics`، `Logs` و `Distributed Tracing` برای تشخیص سریع خرابی‌ها وجود داشته باشند و سناریوهای Failover و Recovery به‌صورت عملی آزمایش شوند.

نکته مهم این است که Scalability، Availability و Fault Tolerance مفاهیم مرتبط اما متفاوتی هستند؛ افزایش تعداد Instanceها به‌تنهایی تضمین‌کننده تحمل خطا نیست.

نتیجه:

برای افزایش Availability و Fault Tolerance از Redundancy، Load Balancing، Horizontal Scaling، Circuit Breaker، Timeout، Retry کنترل‌شده، Health Check و راهکارهای بازیابی Database استفاده می‌کنیم و رفتار سیستم را در برابر خرابی‌های واقعی آزمایش می‌کنیم.

# سؤال ۹

سؤال: برای مدیریت Communication بین سرویس‌های جاوا در معماری Microservices چه راهکارهایی وجود دارد و چه مزایا و معایبی دارند؟

راهنما: ارتباط بین سرویس‌ها می‌تواند همزمان یا غیرهمزمان باشد.

سطح: Senior

### پاسخ

در معماری `Microservices` دو روش اصلی برای ارتباط سرویس‌ها وجود دارد: `Synchronous Communication` و `Asynchronous Communication`.

### ۱. ارتباط همزمان (Synchronous)

در این روش، سرویس فراخواننده درخواست می‌فرستد و معمولاً منتظر پاسخ می‌ماند.

راهکارهای متداول:

- `REST/HTTP`: ساده، رایج و مناسب APIهای مبتنی بر Request/Response.
- `gRPC`: مبتنی بر Protocol Buffers و HTTP/2؛ مناسب ارتباطات داخلی با قراردادهای مشخص و نیاز به کارایی بالا.

مزایا:

- دریافت فوری پاسخ
- سادگی در پیاده‌سازی برخی سناریوهای Request/Response
- مناسب برای Queryهایی که نتیجه باید همان لحظه به کاربر ارائه شود

معایب:

- وابستگی زمانی بین سرویس‌ها
- افزایش Latency در زنجیره فراخوانی‌ها
- انتشار اختلال یک سرویس به سرویس‌های وابسته
- نیاز به مدیریت Timeout، Retry و Circuit Breaker

### ۲. ارتباط غیرهمزمان (Asynchronous)

در این روش، سرویس‌ها از طریق Message Broker یا Event Broker ارتباط برقرار می‌کنند و فرستنده معمولاً منتظر تکمیل پردازش نهایی توسط مصرف‌کننده نمی‌ماند.

ابزارهای متداول:

- `Apache Kafka`: مناسب Event Streaming، پردازش حجم بالای رویدادها و Replay.
- `RabbitMQ`: مناسب Message Queue، Routing و توزیع کار بین Consumerها.

مزایا:

- کاهش وابستگی زمانی بین سرویس‌ها
- امکان Buffer کردن پیام‌ها هنگام افزایش بار
- جداسازی چرخه پردازش سرویس‌ها
- مناسب برای Event-Driven Architecture

معایب:

- پیچیدگی بیشتر در Debugging و Monitoring
- احتمال پردازش تکراری پیام‌ها
- نیاز به مدیریت Eventual Consistency، Ordering و Retry
- دشواری بیشتر در پیاده‌سازی جریان‌های کسب‌وکار چندمرحله‌ای

برای مدیریت این چالش‌ها، استفاده از `Idempotent Consumer`، `Dead Letter Queue` و در سناریوهای مناسب `Transactional Outbox` توصیه می‌شود.

### ۳. انتخاب روش مناسب

- اگر پاسخ فوری لازم است، REST یا gRPC گزینه مناسبی است.
- اگر پردازش می‌تواند در پس‌زمینه انجام شود، Messaging مناسب‌تر است.
- در بسیاری از سیستم‌های Enterprise، معماری ترکیبی بهترین انتخاب است؛ برای مثال REST برای دریافت درخواست و Kafka برای ادامه پردازش غیرهمزمان.

نتیجه:

ارتباط همزمان برای Request/Response فوری مناسب است، درحالی‌که ارتباط غیرهمزمان وابستگی زمانی را کاهش می‌دهد و پردازش مقاوم در برابر نوسان بار را تسهیل می‌کند. انتخاب نهایی باید بر اساس Latency، Coupling، Consistency، حجم پیام و پیچیدگی عملیاتی انجام شود.
# سؤال ۱۱

سؤال: در چه مواقعی استفاده از Mocking در تست‌های جاوا می‌تواند به بهبود سرعت و کیفیت توسعه منجر شود و چه محدودیت‌هایی دارد؟

راهنما: Mocking می‌تواند تست را ساده‌تر کند اما باید محدودیت‌ها را در نظر گرفت.

سطح: Senior

### پاسخ

`Mocking` تکنیکی برای شبیه‌سازی وابستگی‌های یک کلاس در زمان تست است. در جاوا معمولاً از ابزارهایی مانند `Mockito` استفاده می‌کنیم تا رفتار وابستگی‌ها را کنترل کنیم، بدون اینکه نیاز باشد سرویس واقعی آن‌ها اجرا شود.

چه زمانی Mocking مناسب است؟

- وقتی می‌خواهیم یک کلاس را به‌صورت مستقل Unit Test کنیم.
- وقتی وابستگی به سرویس خارجی، Database یا Message Broker وجود دارد.
- وقتی شبیه‌سازی شرایط خطا مانند `Timeout`، `Exception` یا پاسخ نامعتبر لازم است.
- وقتی اجرای وابستگی واقعی هزینه‌بر یا کند است.
- وقتی می‌خواهیم بررسی کنیم یک متد وابستگی با آرگومان‌های مورد انتظار فراخوانی شده است.

مثال با Mockito:

```
@ExtendWith(MockitoExtension.class)
class PaymentServiceTest {

    @Mock
    private PaymentGateway gateway;

    @InjectMocks
    private PaymentService service;

    @Test
    void shouldReturnPaymentResult() {
        when(gateway.pay(100))
                .thenReturn("SUCCESS");

        String result = service.pay(100);

        assertEquals("SUCCESS", result);
    }
}
```

در این مثال، به‌جای ارتباط واقعی با درگاه پرداخت، پاسخ آن را کنترل می‌کنیم.

محدودیت‌ها و معایب:

- Mockها رفتار واقعی Database، شبکه یا سرویس خارجی را تضمین نمی‌کنند.
- Mocking بیش از حد می‌تواند تست را به جزئیات پیاده‌سازی وابسته کند و با هر Refactoring باعث شکست تست شود.
- تست ممکن است موفق باشد، اما سیستم واقعی به دلیل مشکلات Integration همچنان شکست بخورد.
- Mockهای پیچیده ممکن است رفتاری غیرواقعی ایجاد کنند.

بنابراین، باید میان `Unit Test` با Mock و `Integration Test` با وابستگی‌های واقعی یا Test Containerها تعادل برقرار کرد.

نتیجه:

Mocking برای تست سریع و مستقل منطق کلاس‌ها و شبیه‌سازی شرایط خاص مفید است؛ اما جایگزین Integration Test نیست و استفاده بیش از حد از آن می‌تواند تست‌های شکننده و غیرواقعی ایجاد کند.

# سؤال ۱۲

سؤال: چگونه می‌توان تست‌های خودکار را به گونه‌ای طراحی کرد که با تغییرات معماری یا کد، نیاز به بازنویسی گسترده نداشته باشند؟

راهنما: تست‌های مقاوم در برابر تغییرات معماری باید از جزئیات پیاده‌سازی فاصله داشته باشند.

سطح: Senior

### پاسخ

برای طراحی تست‌های پایدار، باید تست‌ها را تا حد امکان به رفتار مورد انتظار سیستم وابسته کنیم، نه به جزئیات داخلی پیاده‌سازی.

تکنیک‌های مهم عبارت‌اند از:

- Behavior-Based Testing: رفتار و خروجی قابل مشاهده را بررسی کنیم، نه ساختار داخلی کلاس‌ها یا ترتیب فراخوانی متدهای خصوصی.
- Testing Through Public Interfaces: تا حد امکان از API عمومی، قرارداد سرویس یا ورودی و خروجی واقعی استفاده کنیم.
- کاهش Mockهای غیرضروری: Mock کردن تمام وابستگی‌ها و بررسی تعداد زیادی از فراخوانی‌های داخلی، تست را شکننده می‌کند.
- Test Pyramid: تعداد مناسبی Unit Test سریع داشته باشیم و در کنار آن Integration Test و تعداد محدودتری End-to-End Test اجرا کنیم.
- Test Data Builders: با استفاده از Factory یا Builder داده‌های تست را خوانا و قابل نگهداری بسازیم.
- Contract Testing: در سیستم‌های توزیع‌شده، قراردادهای بین سرویس‌ها را مستقل از جزئیات پیاده‌سازی بررسی کنیم.
- جداسازی Test Data از منطق تست: از داده‌های ثابت و قابل پیش‌بینی استفاده کنیم و وابستگی به محیط واقعی را کاهش دهیم.
- معنادار بودن Assertionها: به‌جای بررسی جزئیات داخلی، نتیجه کسب‌وکاری مورد انتظار را بررسی کنیم.

برای مثال، اگر پیاده‌سازی `OrderService` از یک الگوریتم داخلی به الگوریتم دیگری تغییر کند، تست باید همچنان معتبر باشد، به شرط اینکه رفتار قابل مشاهده سرویس تغییر نکرده باشد.

البته پایداری تست به معنای بی‌نیازی از تغییر تست نیست. اگر قرارداد یا رفتار مورد انتظار سیستم تغییر کند، تست‌ها نیز باید به‌روزرسانی شوند.

نتیجه:

برای کاهش هزینه نگهداری تست‌ها، رفتار قابل مشاهده را تست می‌کنیم، وابستگی به جزئیات پیاده‌سازی و Mockهای غیرضروری را کاهش می‌دهیم و از Test Pyramid، Contract Testing و Test Data مناسب استفاده می‌کنیم.

# سؤال ۱۳

سؤال: در طراحی وب سرویس‌های RESTful با جاوا، چه راهکارهایی برای مدیریت نسخه‌بندی API باید در نظر گرفته شود؟

راهنما: نسخه‌بندی API برای سازگاری و توسعه آینده اهمیت دارد.

سطح: Senior

### پاسخ

`API Versioning` روشی برای مدیریت تغییرات API است تا بتوانیم قابلیت‌های جدید را اضافه کنیم، بدون اینکه مصرف‌کنندگان فعلی به‌صورت ناخواسته دچار مشکل شوند.

روش‌های متداول نسخه‌بندی عبارت‌اند از:

۱. URI Versioning

نسخه در مسیر URL قرار می‌گیرد:

```
GET /api/v1/orders
GET /api/v2/orders
```

این روش ساده، واضح و در بسیاری از APIهای عمومی رایج است؛ اما ممکن است باعث تکرار مسیرها و کدهای مرتبط شود.

۲. Header Versioning

نسخه از طریق Header مشخص می‌شود:

```
Accept: application/vnd.example.v2+json
```

این روش نسخه را از URI جدا می‌کند، اما ممکن است برای مصرف‌کنندگان و عیب‌یابی پیچیده‌تر باشد.

۳. Query Parameter Versioning

نسخه از طریق Query Parameter مشخص می‌شود:

```
GET /api/orders?version=2
```

این روش ساده است، ولی باید در طراحی Cache و مستندسازی به نحوه تأثیر پارامتر بر پاسخ توجه شود.

### اصول مهم در مدیریت نسخه‌ها

- تا جای ممکن تغییرات `Backward-Compatible` ایجاد کنیم؛ مانند افزودن فیلد اختیاری جدید.
- از حذف یا تغییر معنای فیلدهای موجود بدون برنامه مهاجرت خودداری کنیم.
- برای نسخه‌های قدیمی سیاست Deprecation و زمان پایان پشتیبانی مشخص کنیم.
- مستندات هر نسخه را با ابزارهایی مانند OpenAPI نگهداری کنیم.
- تست‌های Contract و Integration را برای نسخه‌های پشتیبانی‌شده اجرا کنیم.
- مصرف‌کنندگان را از تغییرات ناسازگار و زمان بازنشستگی نسخه مطلع کنیم.
- برای جلوگیری از تکرار منطق، در صورت امکان Business Logic مشترک را بین نسخه‌ها استفاده کنیم.

در Spring Boot می‌توان با تنظیم Mappingها و DTOهای جداگانه، نسخه‌های مختلف را مدیریت کرد؛ اما نباید بدون نیاز واقعی برای هر نسخه یک پیاده‌سازی کاملاً مستقل ایجاد کرد.

نتیجه:

نسخه‌بندی API باید با هدف حفظ Backward Compatibility و مدیریت تغییرات انجام شود. انتخاب روش URI، Header یا Query Parameter اهمیت دارد، اما سیاست مهاجرت، مستندسازی، تست قرارداد و بازنشستگی نسخه‌ها به همان اندازه مهم هستند.

# سؤال ۱۴

سؤال: در پیاده‌سازی Web Service با جاوا، چگونه می‌توان امنیت داده‌ها را تضمین کرد و چه تهدیدهایی باید در نظر گرفته شود؟

راهنما: امنیت وب سرویس‌ها نیازمند توجه به تهدیدهای رایج و پیاده‌سازی راهکارهای مناسب است.

سطح: Senior

### پاسخ

امنیت Web Service باید در چند لایه پیاده‌سازی شود؛ از ارتباط شبکه‌ای و احراز هویت گرفته تا کنترل دسترسی، اعتبارسنجی ورودی و حفاظت از داده‌ها.

۱. ارتباط امن با HTTPS

استفاده از `TLS` مانع شنود و دست‌کاری داده‌ها در مسیر انتقال می‌شود. گواهی‌ها و تنظیمات TLS نیز باید به‌درستی مدیریت شوند.

۲. Authentication و Authorization

- `Authentication` مشخص می‌کند درخواست‌کننده چه کسی است.
- `Authorization` تعیین می‌کند درخواست‌کننده به چه منابع و عملیاتی دسترسی دارد.

باید از روش‌های مناسب مانند OAuth 2.0 و OpenID Connect استفاده کرد و دسترسی به منابع را در سطح عملیات و داده کنترل کرد.

۳. Input Validation

تمام ورودی‌ها باید از نظر نوع، طول، قالب و محدودیت‌های کسب‌وکار اعتبارسنجی شوند. همچنین باید در برابر تهدیدهایی مانند SQL Injection، دست‌کاری داده‌ها و ورودی‌های مخرب محافظت ایجاد کرد.

۴. مدیریت Session و Token

Tokenها باید به‌درستی اعتبارسنجی شوند؛ از جمله امضا، زمان انقضا و Claimهای مورد نیاز. Secretها نیز نباید در Source Code یا Logها قرار گیرند.

۵. Rate Limiting و مقابله با DoS

برای جلوگیری از سوءاستفاده و مصرف بیش از حد منابع باید محدودیت نرخ درخواست، Timeout و محدودیت اندازه Request اعمال شود.

۶. حفاظت از داده‌های حساس

- داده‌های حساس نباید در پاسخ‌ها یا Logها افشا شوند.
- اطلاعات حساس ذخیره‌شده باید متناسب با ریسک رمزنگاری شوند.
- دسترسی‌ها باید بر اساس اصل `Least Privilege` تنظیم شوند.

۷. مدیریت خطا و Dependencyها

پیام خطا نباید Stack Trace، اطلاعات Database یا جزئیات داخلی سیستم را به کاربر افشا کند. همچنین Dependencyها باید از نظر آسیب‌پذیری بررسی شوند.

در پروژه‌های Spring Boot می‌توان از Spring Security، Bean Validation، مدیریت متمرکز Exceptionها و ابزارهای Security Scanning استفاده کرد.

نتیجه:

امنیت Web Service با ترکیب HTTPS، Authentication، Authorization، اعتبارسنجی ورودی، مدیریت امن Token، Rate Limiting، حفاظت از داده‌های حساس و کنترل دسترسی حاصل می‌شود. هیچ راهکار منفردی برای تضمین کامل امنیت کافی نیست.

# سؤال ۱۵

سؤال: در انتخاب بین SOAP و REST برای پیاده‌سازی سرویس‌های جاوا، چه معیارهایی باید لحاظ شود؟

راهنما: انتخاب پروتکل باید بر اساس نیازهای پروژه و ویژگی‌های هر پروتکل انجام شود.

سطح: Senior

### پاسخ

برای انتخاب بین `SOAP` و `REST` باید نوع تعامل، قرارداد سرویس، نیازهای امنیتی، پیچیدگی Integration و محدودیت‌های سیستم را بررسی کنیم.

### SOAP

`SOAP` یک پروتکل پیام‌رسانی است که معمولاً از XML برای قالب پیام استفاده می‌کند و می‌تواند از قابلیت‌های استاندارد خانواده WS-\* بهره ببرد.

مزایا:

- قرارداد رسمی سرویس با `WSDL`
- پشتیبانی از استانداردهایی مانند `WS-Security`
- مناسب برای برخی Integrationهای سازمانی با قراردادهای سخت‌گیرانه
- قابلیت استفاده از الگوهای مختلف انتقال پیام

معایب:

- پیام‌های XML معمولاً حجیم‌تر هستند.
- پیاده‌سازی و عیب‌یابی می‌تواند پیچیده‌تر باشد.
- سربار پردازش و ساختار پیام ممکن است بیشتر باشد.

### REST

`REST` یک Architectural Style است، نه یک پروتکل مستقل. سرویس‌های RESTful معمولاً از HTTP و قالب‌هایی مانند JSON استفاده می‌کنند.

مزایا:

- سادگی و خوانایی بیشتر در بسیاری از APIها
- سازگاری گسترده با Web و Mobile
- استفاده از قابلیت‌های HTTP مانند Status Code، Cache و Methodها
- مناسب برای APIهای سبک و Resource-Oriented

معایب:

- قرارداد رسمی و قابلیت‌های پیشرفته SOAP به‌صورت ذاتی در همه APIهای REST وجود ندارد؛ باید با ابزارها و طراحی مناسب فراهم شوند.
- مدیریت بعضی از جریان‌های پیچیده سازمانی نیازمند طراحی اضافی است.

### معیار انتخاب

- اگر Integration سازمانی به WSDL یا استانداردهای WS-\* وابسته است، SOAP می‌تواند مناسب‌تر باشد.
- اگر API ساده، سبک و سازگار با Web یا Mobile نیاز داریم، REST معمولاً انتخاب مناسب‌تری است.
- اگر امنیت پیچیده مورد نیاز است، باید نیاز واقعی را بررسی کنیم؛ REST هم می‌تواند با OAuth 2.0، TLS و کنترل دسترسی مناسب، امن باشد.
- باید سازگاری با سیستم‌های موجود، قراردادهای مصرف‌کنندگان، ابزارهای تیم و هزینه نگهداری را نیز در نظر بگیریم.

نتیجه:

SOAP برای سرویس‌هایی با قرارداد رسمی و نیازهای خاص استانداردهای WS-\* مناسب است؛ REST معمولاً برای APIهای ساده و Web-oriented انتخاب بهتری است. تصمیم نهایی باید بر اساس نیازهای فنی و سازمانی گرفته شود، نه صرفاً سرعت یا محبوبیت.

# سؤال ۱۶

سؤال: در پروژه‌های Spring، چگونه می‌توان Dependency Injection را بهینه و بدون ایجاد پیچیدگی بیش از حد پیاده‌سازی کرد؟

راهنما: Dependency Injection باید ساده و قابل نگهداری باشد.

سطح: Senior

### پاسخ

`Dependency Injection (DI)` روشی برای تأمین وابستگی‌های یک کلاس از بیرون آن است. در Spring، معمولاً `IoC Container` مسئول ساخت و مدیریت Beanها و تزریق وابستگی‌های آن‌هاست.

برای پیاده‌سازی ساده و قابل نگهداری، نکات زیر مهم هستند:

- Constructor Injection: روش پیش‌فرض مناسبی است؛ زیرا وابستگی‌های ضروری را صریح می‌کند و امکان تعریف فیلدهای `final` را فراهم می‌سازد.
- وابستگی به Abstraction: در صورت نیاز به تعویض پیاده‌سازی یا جداسازی قرارداد از جزئیات، از Interface استفاده می‌کنیم؛ نه اینکه برای هر کلاس به‌صورت خودکار Interface بسازیم.
- Single Responsibility Principle: اگر یک کلاس وابستگی‌های بسیار زیادی دارد، ممکن است مسئولیت‌های متعددی را بر عهده گرفته باشد. باید طراحی آن را بررسی کنیم، نه اینکه صرفاً وابستگی‌ها را در کلاس‌های بیشتری پخش کنیم.
- استفاده از Annotationهای استاندارد Spring: مانند `@Component`، `@Service` و `@Repository` برای ثبت Beanها و `@Configuration` و `@Bean` برای پیکربندی‌های صریح.
- پرهیز از Field Injection: تزریق مستقیم به فیلدها وابستگی‌ها را پنهان می‌کند و تست مستقل را دشوارتر می‌سازد.
- مدیریت ابهام در Beanها: اگر چند Bean از یک نوع وجود داشته باشند، از `@Qualifier` یا در صورت مناسب بودن `@Primary` استفاده می‌کنیم.
- پرهیز از پیچیدگی غیرضروری: استفاده از Factoryهای سفارشی، چرخه‌های وابستگی پیچیده و تزریق‌های غیرمستقیم باید توجیه مشخصی داشته باشد.

مثال:

```
@Service
public class OrderService {

    private final PaymentService paymentService;

    public OrderService(PaymentService paymentService) {
        this.paymentService = paymentService;
    }
}
```

در این مثال، Spring وابستگی `PaymentService` را هنگام ساخت `OrderService` تزریق می‌کند. اگر تنها یک Constructor وجود داشته باشد، معمولاً نیازی به `@Autowired` روی آن نیست.

نتیجه:

برای DI بهینه در Spring، از Constructor Injection، وابستگی‌های صریح، Abstractionهای معنادار و مسئولیت‌های مشخص استفاده می‌کنیم. هدف، کاهش Coupling و افزایش Testability است، نه ایجاد لایه‌ها و Interfaceهای غیرضروری.

# سؤال ۱۷

سؤال: در Spring Boot، چه راهکارهایی برای مدیریت Configuration در محیط‌های مختلف وجود دارد؟

راهنما: مدیریت کانفیگ در محیط‌های مختلف اهمیت بالایی دارد.

سطح: Senior

### پاسخ

در پروژه‌های Spring Boot، تنظیمات باید به‌گونه‌ای مدیریت شوند که یک Artifact واحد بتواند در محیط‌های مختلف مانند Development، Test و Production اجرا شود، بدون اینکه نیاز به تغییر Source Code داشته باشیم.

راهکارهای اصلی عبارت‌اند از:

۱. Externalized Configuration

تنظیمات را از کد جدا می‌کنیم و از فایل‌هایی مانند `application.properties` یا `application.yml` استفاده می‌کنیم.

۲. Spring Profiles

برای تنظیمات اختصاصی هر محیط از Profileها استفاده می‌کنیم:

```
# application.yml
spring:
  application:
    name: order-service
```

```
# application-prod.yml
logging:
  level:
    root: WARN
```

با فعال کردن Profile مربوط به Production، تنظیمات اختصاصی آن محیط اعمال می‌شوند. می‌توان Profile را از طریق Environment Variable یا تنظیمات Deployment فعال کرد.

۳. Environment Variables

مقادیر وابسته به محیط، مانند آدرس سرویس‌ها و تنظیمات اتصال، می‌توانند از طریق Environment Variable تأمین شوند. این روش برای Containerها و CI/CD مناسب است.

۴. مدیریت امن Secretها

مواردی مانند Database Password، API Key و Token نباید در Git یا فایل‌های عمومی Configuration ذخیره شوند. برای این موارد از Secret Manager یا سازوکار امن زیرساخت استفاده می‌کنیم.

۵. استفاده از `@ConfigurationProperties`

برای گروه‌بندی و اعتبارسنجی تنظیمات مرتبط، از `@ConfigurationProperties` استفاده می‌کنیم.

```
@ConfigurationProperties(prefix = "payment")
@Validated
public record PaymentProperties(
        @NotBlank String baseUrl,
        @Min(1) int timeoutSeconds
) {}
```

با فعال‌سازی مناسب Configuration Properties، مقادیر به این کلاس Bind می‌شوند و تنظیمات نامعتبر می‌توانند هنگام راه‌اندازی شناسایی شوند.

۶. مدیریت اولویت تنظیمات

Spring Boot چندین منبع Configuration دارد و اولویت آن‌ها بر نتیجه نهایی اثر می‌گذارد. باید مشخص باشد مقدار نهایی از کجا تأمین می‌شود تا تنظیمات محیطی به‌صورت ناخواسته Override نشوند.

۷. مدیریت تغییرات Configuration

تغییر تنظیمات حساس باید کنترل‌شده، قابل ردیابی و در صورت نیاز قابل بازگشت باشد. همچنین نباید فرض کنیم همه تغییرات Configuration بدون Restart اعمال می‌شوند.

نتیجه:

برای مدیریت Configuration در Spring Boot، از Externalized Configuration، Profiles، Environment Variables، `@ConfigurationProperties` و Secret Manager استفاده می‌کنیم. هدف این است که تنظیمات محیط‌ها جدا، اعتبارسنجی‌شده، امن و قابل نگهداری باشند.

# سؤال ۱۸

سؤال: در پروژه‌های بزرگ Spring، چگونه می‌توان از AOP برای مدیریت Concernهای مشترک مانند Logging و Security بهره برد؟

راهنما: AOP برای جداسازی Concernهای مشترک کاربرد دارد.

سطح: Senior

### پاسخ

`Aspect-Oriented Programming (AOP)` امکان جداسازی Concernهای مشترک یا `Cross-Cutting Concerns` را از منطق اصلی کسب‌وکار فراهم می‌کند.

برای مثال، Logging، اندازه‌گیری زمان اجرا، Audit و برخی کنترل‌های دسترسی ممکن است در بخش‌های متعددی از برنامه مورد نیاز باشند. به‌جای تکرار این منطق در همه متدها، می‌توان آن را در یک `Aspect` قرار داد.

مفاهیم اصلی AOP عبارت‌اند از:

- `Aspect`: ماژولی که Concern مشترک را پیاده‌سازی می‌کند.
- `Join Point`: نقطه‌ای از اجرای برنامه که می‌توان Advice را در آن اعمال کرد.
- `Pointcut`: شرط انتخاب نقاطی که Advice باید روی آن‌ها اجرا شود.
- `Advice`: عملیاتی که قبل، بعد یا در اطراف نقطه انتخاب‌شده اجرا می‌شود.

مثال در Spring:

```
@Aspect
@Component
public class ExecutionLoggingAspect {

    @Around("within(com.example.service..*)")
    public Object logExecution(ProceedingJoinPoint joinPoint)
            throws Throwable {

        long start = System.nanoTime();

        try {
            return joinPoint.proceed();
        } finally {
            long elapsed = System.nanoTime() - start;
            // Record execution time using a metrics system.
        }
    }
}
```

این Aspect زمان اجرای متدهای محدوده انتخاب‌شده را اندازه‌گیری می‌کند. در Production بهتر است برای Metrics از ابزارهایی مانند Micrometer استفاده کنیم و از ثبت داده‌های حساس یا پرحجم در Logها بپرهیزیم.

ملاحظات مهم:

- Pointcutها باید محدود و مشخص باشند تا Advice ناخواسته روی متدهای زیادی اجرا نشود.
- AOP نباید جایگزین طراحی صحیح منطق کسب‌وکار شود.
- ترتیب اجرای چند Aspect ممکن است مهم باشد.
- در Spring AOP، رفتار معمولاً بر پایه Proxy است؛ بنابراین فراخوانی یک متد از متد دیگر همان Bean یا `Self-Invocation` معمولاً از Proxy عبور نمی‌کند و ممکن است Advice اجرا نشود.
- AOP به‌تنهایی جایگزین کامل Spring Security نیست؛ برای امنیت، بهتر است از سازوکارهای تخصصی و آزموده‌شده Spring Security استفاده کنیم.

نتیجه:

AOP برای جداسازی Logging، Metrics و سایر Cross-Cutting Concerns مناسب است. با انتخاب دقیق Pointcutها، شناخت محدودیت Proxyها و پرهیز از پیچیده کردن منطق کسب‌وکار، می‌توان از آن به‌صورت مؤثر استفاده کرد.

# سؤال ۱۹

سؤال: در چه شرایطی استفاده از Singleton Pattern در جاوا می‌تواند مشکلاتی ایجاد کند و چگونه می‌توان این مشکلات را برطرف کرد؟

راهنما: Singleton باید با توجه به نیازهای پروژه و محیط اجرا انتخاب شود.

سطح: Senior

### پاسخ

`Singleton Pattern` تضمین می‌کند که در یک محدوده مشخص، تنها یک نمونه از یک کلاس وجود داشته باشد و دسترسی مشترکی به آن فراهم شود.

این الگو زمانی می‌تواند مشکل‌ساز شود که نمونه Singleton دارای State قابل تغییر باشد یا وابستگی‌های آن به‌صورت سراسری و پنهان در دسترس قرار گیرند.

مشکلات رایج:

- Thread Safety: چند Thread ممکن است هم‌زمان State مشترک را تغییر دهند و باعث Race Condition شوند.
- Global State: وابستگی به Singletonهای سراسری، تغییر رفتار سیستم و تست مستقل را دشوار می‌کند.
- Tight Coupling: کلاس‌ها مستقیماً به Singleton وابسته می‌شوند و جایگزینی پیاده‌سازی دشوارتر می‌شود.
- Testing Difficulty: State باقی‌مانده از یک تست می‌تواند روی تست بعدی اثر بگذارد.
- Lifecycle Issues: مدیریت ایجاد، آزادسازی منابع و چرخه عمر نمونه ممکن است پیچیده شود.
- Distributed Deployment: Singleton در یک JVM به معنای Singleton در کل سیستم توزیع‌شده نیست؛ هر Instance برنامه ممکن است نمونه مستقل خود را داشته باشد.

راهکارهای پیشنهادی:

- در صورت امکان، Singleton را Stateless طراحی کنیم.
- برای مدیریت هم‌زمانی، از سازوکارهای مناسب مانند `synchronized`، `volatile` یا کلاس‌های `java.util.concurrent` استفاده کنیم؛ انتخاب به نوع عملیات بستگی دارد.
- به‌جای Global Access، وابستگی‌ها را با Constructor Injection تأمین کنیم.
- در برنامه‌های Spring، از Scope پیش‌فرض `singleton` برای Beanهایی استفاده کنیم که واقعاً به یک نمونه مشترک در همان `ApplicationContext` نیاز دارند.
- برای نیاز به هماهنگی بین چند Instance، از سازوکارهای توزیع‌شده مناسب استفاده کنیم؛ نه Singleton محلی JVM.

نکته مهم این است که Singleton در Spring معمولاً یک Bean در هر `ApplicationContext` است، نه الزاماً یک نمونه در کل JVM یا کل زیرساخت.

نتیجه:

Singleton برای مدیریت یک نمونه مشترک در محدوده مشخص مفید است، اما State قابل تغییر، Global State و Thread Safety می‌توانند مشکل‌ساز شوند. طراحی Stateless، Dependency Injection و انتخاب صحیح محدوده Singleton به کاهش این مشکلات کمک می‌کند.

# سؤال ۲۰

سؤال: در پروژه‌های جاوا، چه زمانی استفاده از Factory Pattern مناسب است و چه مزایایی نسبت به پیاده‌سازی مستقیم دارد؟

راهنما: Factory Pattern می‌تواند انعطاف‌پذیری و توسعه‌پذیری کد را افزایش دهد.

سطح: Senior

### پاسخ

`Factory Pattern` الگویی برای متمرکز کردن منطق ایجاد Objectهاست. به‌جای اینکه کد مصرف‌کننده مستقیماً با Constructorها و جزئیات ساخت چند نوع Object درگیر شود، ایجاد نمونه به یک Factory واگذار می‌شود.

این الگو زمانی مناسب است که:

- چند پیاده‌سازی از یک Interface وجود دارد و انتخاب آن‌ها به شرایط وابسته است.
- منطق ساخت Object پیچیده است.
- ایجاد Object نیازمند چند مرحله یا تنظیمات مختلف است.
- می‌خواهیم جزئیات ایجاد Object را از Business Logic جدا کنیم.
- ساخت Objectها باید به‌صورت متمرکز مدیریت شود.

مثال:

```
interface NotificationSender {
    void send(String message);
}

class EmailSender implements NotificationSender {
    public void send(String message) {
        // Send email
    }
}

class SmsSender implements NotificationSender {
    public void send(String message) {
        // Send SMS
    }
}
```

Factory:

```
class NotificationFactory {

    public NotificationSender create(String type) {
        return switch (type) {
            case "EMAIL" -> new EmailSender();
            case "SMS" -> new SmsSender();
            default -> throw new IllegalArgumentException(
                    "Unsupported notification type: " + type);
        };
    }
}
```

در این مثال، کد مصرف‌کننده به‌جای ساخت مستقیم `EmailSender` یا `SmsSender` از Factory استفاده می‌کند.

مزایا:

- جداسازی منطق ساخت Object از منطق کسب‌وکار
- کاهش وابستگی کد مصرف‌کننده به پیاده‌سازی‌های مشخص
- متمرکز شدن قواعد ایجاد و انتخاب پیاده‌سازی
- آسان‌تر شدن تغییر یا اضافه کردن برخی پیاده‌سازی‌ها

محدودیت‌ها:

- Factory ساده‌ای که فقط Constructor را فراخوانی می‌کند ممکن است ارزش خاصی ایجاد نکند.
- افزودن انواع جدید ممکن است همچنان نیازمند تغییر Factory باشد.
- اگر Factory بیش از حد بزرگ شود، می‌تواند به یک کلاس پیچیده و متمرکز تبدیل شود.

در Spring، بسیاری از موارد ساخت Bean را می‌توان به Container واگذار کرد. برای انتخاب پویا بین پیاده‌سازی‌ها نیز می‌توان از Map مبتنی بر Beanها، Strategy Pattern یا Factoryهای کوچک و هدفمند استفاده کرد.

نتیجه:

Factory Pattern زمانی مناسب است که منطق ایجاد Object یا انتخاب پیاده‌سازی پیچیده یا متغیر باشد. این الگو ساخت Object را از Business Logic جدا می‌کند، اما برای ساخت‌های ساده نباید بدون نیاز واقعی به آن پیچیدگی اضافه کرد.

# سؤال ۲۱

سؤال: در پیاده‌سازی Observer Pattern با جاوا، چه چالش‌هایی در مدیریت منابع و عملکرد وجود دارد؟

راهنما: Observer Pattern می‌تواند باعث ایجاد پیچیدگی در مدیریت منابع شود.

سطح: Senior

### پاسخ

در `Observer Pattern`، یک `Subject` تغییرات خود را به چندین `Observer` اطلاع می‌دهد. این الگو وابستگی مستقیم بین اجزا را کاهش می‌دهد، اما در سیستم‌های بزرگ چالش‌هایی در مدیریت منابع و عملکرد ایجاد می‌کند.

۱. Memory Leak

اگر `Observer` ثبت‌شده دیگر موردنیاز نباشد اما از `Subject` حذف نشود، همچنان ممکن است در حافظه باقی بماند؛ زیرا `Subject` به آن reference دارد.

راهکار:

- حذف Observer با `removeObserver()`.
- استفاده از سازوکارهای ثبت و لغو ثبت خودکار، مثلاً در lifecycle کامپوننت‌ها.
- در شرایط مناسب، استفاده از `WeakReference`؛ البته این روش جایگزین مدیریت صحیح lifecycle نیست.

۲. مشکلات عملکردی

اگر تعداد Observerها زیاد باشد، اطلاع‌رسانی به همه آن‌ها می‌تواند هزینه‌بر شود. اجرای هم‌زمان و مستقیم callbackها نیز ممکن است باعث افزایش latency شود.

راهکار:

- استفاده از پردازش asynchronous با `ExecutorService` در صورت نیاز.
- محدود کردن کار هر Observer و جلوگیری از عملیات سنگین در callback.
- استفاده از batching یا event filtering در سیستم‌های پرترافیک.

۳. Thread Safety

اگر چند Thread هم‌زمان Observerها را ثبت، حذف یا فراخوانی کنند، احتمال بروز `Race Condition` وجود دارد.

راهکار: استفاده از ساختارهای داده thread-safe، مدیریت مناسب synchronization و تعریف روشن رفتار سیستم هنگام ثبت یا حذف Observer در حین انتشار event.

۴. مدیریت Exceptionها

اگر یک Observer هنگام پردازش event خطا بدهد، ممکن است اطلاع‌رسانی به Observerهای بعدی مختل شود. بهتر است خطاها به‌صورت کنترل‌شده مدیریت و ثبت شوند.

۵. ترتیب اجرا و بازگشت بازگشتی

در پیاده‌سازی synchronous، ترتیب اجرا می‌تواند بر نتیجه اثر بگذارد. همچنین اگر Observer دوباره باعث انتشار event شود، ممکن است زنجیره‌ای از فراخوانی‌های بازگشتی ایجاد شود.

نتیجه: برای استفاده مؤثر از Observer Pattern باید lifecycle، لغو ثبت، Thread Safety، مدیریت Exception و هزینه انتشار event را کنترل کرد. در سیستم‌های پرترافیک، طراحی asynchronous و event-driven می‌تواند مناسب‌تر باشد.

# سؤال ۲۲

سؤال: در جاوا، چگونه می‌توان تصمیم گرفت که از Interface یا Abstract Class برای پیاده‌سازی یک ویژگی استفاده شود؟

راهنما: انتخاب بین Interface و Abstract Class به نیازهای پروژه بستگی دارد.

سطح: Senior

### پاسخ

هر دو برای abstraction و طراحی قابل توسعه کاربرد دارند، اما اهداف متفاوتی دارند.

۱. چه زمانی از Interface استفاده کنیم؟

وقتی می‌خواهیم یک قرارداد رفتاری تعریف کنیم که پیاده‌سازی‌های مختلف بتوانند آن را مستقل از سلسله‌مراتب وراثت اجرا کنند.

مزایا:

- یک کلاس می‌تواند چندین Interface را پیاده‌سازی کند.
- وابستگی به پیاده‌سازی مشخص کاهش می‌یابد.
- برای Dependency Injection و تست‌پذیری مناسب است.
- امکان پیاده‌سازی `default` و `static` method وجود دارد.

مثال:

```
public interface PaymentProcessor {
    void processPayment(long amount);
}

public class OnlinePaymentProcessor
        implements PaymentProcessor {

    @Override
    public void processPayment(long amount) {
        // Process online payment
    }
}
```

۲. چه زمانی از Abstract Class استفاده کنیم؟

وقتی چند کلاس علاوه بر قرارداد مشترک، به state، constructor یا پیاده‌سازی مشترک نیاز دارند.

مثال:

```
public abstract class BasePaymentProcessor {

    protected final String provider;

    protected BasePaymentProcessor(String provider) {
        this.provider = provider;
    }

    public void logPayment() {
        System.out.println("Provider: " + provider);
    }

    public abstract void processPayment(long amount);
}
```

در این مثال، کلاس پایه state و رفتار مشترک را نگه می‌دارد و جزئیات پردازش را به زیرکلاس‌ها واگذار می‌کند.

۳. معیارهای تصمیم‌گیری

- Contract: اگر هدف اصلی تعریف قرارداد است، `Interface` معمولاً انتخاب مناسب‌تری است.
- Shared State and Implementation: اگر state و منطق مشترک واقعی داریم، `Abstract Class` می‌تواند مناسب باشد.
- Multiple Inheritance of Type: جاوا اجازه پیاده‌سازی چند Interface را می‌دهد، اما وراثت از چند کلاس را نمی‌دهد.
- Evolution: تغییر Interfaceهای عمومی باید با توجه به سازگاری پیاده‌سازی‌های موجود انجام شود.
- Composition: اگر رفتار مشترک را می‌توان در یک کامپوننت مستقل قرار داد، `Composition` ممکن است از ایجاد سلسله‌مراتب پیچیده وراثت بهتر باشد.

نتیجه: برای تعریف قابلیت‌ها و قراردادها معمولاً از `Interface` استفاده می‌کنیم؛ برای اشتراک state و رفتار پایه میان کلاس‌های مرتبط، `Abstract Class` مناسب است. تصمیم باید بر اساس نیاز طراحی باشد، نه صرفاً ترجیح شخصی.

# سؤال ۲۳

سؤال: در مدیریت Exceptionها در جاوا، چه استراتژی‌هایی برای جلوگیری از نشت اطلاعات حساس باید لحاظ شود؟

راهنما: مدیریت Exceptionها باید امنیت و خوانایی را تضمین کند.

سطح: Senior

### پاسخ

در مدیریت Exceptionها باید بین اطلاعات موردنیاز برای عیب‌یابی و اطلاعاتی که نباید در اختیار کاربر یا مهاجم قرار بگیرند، تفاوت قائل شویم.

۱. جداسازی پیام داخلی از پیام کاربر

جزئیات Exception ممکن است شامل SQL، مسیر فایل، نام کلاس‌ها، اطلاعات زیرساخت یا داده‌های حساس باشد. این اطلاعات نباید مستقیماً به کاربر نمایش داده شوند.

```
try {
    paymentService.processPayment(request);
} catch (PaymentException ex) {
    logger.error("Payment processing failed", ex);

    throw new ApiException(
        "PAYMENT_FAILED",
        "پردازش پرداخت ناموفق بود"
    );
}
```

در این مثال، جزئیات فنی برای عیب‌یابی ثبت می‌شوند و کاربر یک پیام عمومی دریافت می‌کند.

۲. جلوگیری از نمایش Stack Trace

در محیط Production نباید `stack trace` یا جزئیات داخلی Exception در HTTP response نمایش داده شود. در Spring Boot می‌توان تنظیمات خطا را کنترل کرد، از جمله غیرفعال‌کردن نمایش جزئیات و Stack Trace در پاسخ‌های عمومی.

۳. ثبت امن Logها

ثبت Exception برای عیب‌یابی ضروری است، اما Logها نیز می‌توانند محل نشت اطلاعات باشند.

- رمز عبور، Token، اطلاعات کارت و داده‌های شخصی را ثبت نکنید.
- داده‌های ورودی کاربر را پیش از ثبت اعتبارسنجی یا پاک‌سازی کنید.
- برای جلوگیری از `Log Injection`، کاراکترهای کنترلی را مدیریت کنید.
- دسترسی به Logها و مدت نگهداری آن‌ها را محدود کنید.

۴. مدیریت Exception در لایه مناسب

Exceptionها را در مرز مناسب سیستم مدیریت کنید؛ برای مثال، در API از `@ControllerAdvice` برای تبدیل خطاهای داخلی به پاسخ استاندارد استفاده کنید.

```
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(PaymentException.class)
    public ResponseEntity<ApiError> handlePaymentException(
            PaymentException ex) {

        return ResponseEntity
            .status(HttpStatus.BAD_GATEWAY)
            .body(new ApiError(
                "PAYMENT_FAILED",
                "پرداخت در حال حاضر قابل انجام نیست"
            ));
    }
}
```

کد پاسخ باید با ماهیت واقعی خطا سازگار باشد؛ برای مثال، خطای اعتبارسنجی معمولاً به `400` و خطای غیرمنتظره به `500` مربوط است.

۵. حفظ علت اصلی خطا در داخل سیستم

در صورت نیاز، می‌توان از `exception chaining` برای حفظ علت اصلی استفاده کرد:

```
throw new PaymentException(
    "Payment operation failed",
    cause
);
```

اما نباید `cause` یا پیام آن بدون بررسی به پاسخ عمومی API منتقل شود.

۶. جلوگیری از افشای اطلاعات از طریق پیام خطا

پیام خطا نباید مشخص کند که مثلاً یک حساب کاربری وجود دارد یا خیر، مگر اینکه این اطلاعات طبق سیاست امنیتی سیستم قابل افشا باشد. همچنین خطاهای داخلی نباید ساختار پایگاه داده یا تنظیمات سیستم را آشکار کنند.

نتیجه: پیام عمومی و استاندارد برای کاربر، Log امن برای تیم فنی، کنترل Stack Trace، حذف داده‌های حساس از Log و مدیریت مرکزی Exceptionها، مهم‌ترین راهکارهای جلوگیری از Information Disclosure هستند.

# سؤال ۲۴

سؤال: در پروژه‌های جاوا، چگونه می‌توان از ویژگی‌های جدید زبان مانند Records و Sealed Classes برای بهبود طراحی استفاده کرد؟

راهنما: ویژگی‌های جدید جاوا می‌توانند طراحی کد را ساده‌تر و ایمن‌تر کنند.

سطح: Senior

### پاسخ

`Records` و `Sealed Classes` از ویژگی‌های جاوا هستند که می‌توانند boilerplate را کاهش دهند و محدودیت‌های طراحی را به‌صورت صریح در کد بیان کنند.

۱. Records

`Record` برای مدل‌سازی داده‌هایی مناسب است که هویت آن‌ها بر اساس مقادیرشان تعریف می‌شود؛ مانند DTOها، خروجی APIها و اشیای انتقال داده.

```
public record CustomerDto(
    Long id,
    String name,
    String email
) {}
```

جاوا به‌صورت خودکار constructor، accessorها، `equals()`، `hashCode()` و `toString()` مناسب را تولید می‌کند.

مزایا:

- کاهش کد تکراری.
- بیان روشن مدل‌های داده‌ای.
- رفتار value-based برای مقایسه اشیا.

نکات مهم:

- Recordها به‌طور ضمنی `final` هستند و نمی‌توان از آن‌ها subclass ساخت.
- فیلدهای component به‌صورت نهایی تعریف می‌شوند، اما این ویژگی به معنی immutable بودن عمیق تمام اشیای داخلی نیست.
- برای Entityهای JPA که به هویت پایدار، تغییرپذیری یا سازوکارهای proxy نیاز دارند، معمولاً انتخاب مناسبی نیستند.

۲. Sealed Classes

`Sealed Classes` مشخص می‌کنند که کدام کلاس‌ها یا Interfaceها اجازه دارند یک نوع را توسعه دهند یا پیاده‌سازی کنند.

مثال:

```
public sealed interface PaymentResult
        permits Success, Failure {
}

public record Success(String transactionId)
        implements PaymentResult {
}

public record Failure(String reason)
        implements PaymentResult {
}
```

در این طراحی، مجموعه پیاده‌سازی‌های مستقیم `PaymentResult` محدود و مشخص است.

مزایا:

- جلوگیری از ایجاد پیاده‌سازی‌های پیش‌بینی‌نشده.
- مناسب برای مدل‌سازی حالت‌های محدود دامنه.
- امکان استفاده مؤثرتر از `pattern matching` و `switch` در نسخه‌های جدید جاوا.

مثلاً:

```
String describe(PaymentResult result) {
    return switch (result) {
        case Success s -> "Success: " + s.transactionId();
        case Failure f -> "Failure: " + f.reason();
    };
}
```

در این مثال، با توجه به اینکه مجموعه حالت‌ها بسته و قابل بررسی است، کامپایلر می‌تواند کامل بودن `switch` را بررسی کند.

۳. چگونه در طراحی واقعی استفاده کنیم؟

- برای DTOها و داده‌های immutable، `Record` را بررسی کنید.
- برای نتیجه‌های محدود مانند `Success`، `Failure` و `Pending` از `Sealed Interface` استفاده کنید.
- برای انواع باز و قابل توسعه، از `Interface` معمولی استفاده کنید.
- از این ویژگی‌ها صرفاً به دلیل جدید بودن استفاده نکنید؛ نیاز واقعی دامنه باید دلیل انتخاب باشد.

نتیجه: `Records` مدل‌سازی داده را ساده‌تر می‌کنند و `Sealed Classes` مجموعه انواع مجاز را محدود می‌کنند. ترکیب آن‌ها می‌تواند کد را کم‌حجم‌تر، قابل فهم‌تر و از نظر نوع ایمن‌تر کند.

# سؤال ۲۵

سؤال: در طراحی سیستم‌های بزرگ جاوا، چگونه می‌توان اصل SRP را رعایت کرد و چه مزایایی دارد؟

راهنما: SRP یکی از اصول مهم طراحی شی‌گرا است.

سطح: Senior

### پاسخ

اصل `Single Responsibility Principle (SRP)` از اصول `SOLID` است. طبق تعریف رایج رابرت مارتین، هر ماژول یا کلاس باید یک دلیل برای تغییر داشته باشد؛ یعنی مسئولیت‌های آن باید حول یک محور منسجم تغییر متمرکز باشند.

۱. شناسایی مسئولیت‌های مستقل

فرض کنید یک کلاس هم‌زمان:

- قوانین تجاری پرداخت را اجرا می‌کند.
- درخواست HTTP ارسال می‌کند.
- اطلاعات را در دیتابیس ذخیره می‌کند.
- گزارش و Log تولید می‌کند.

این کلاس به دلایل متفاوتی ممکن است تغییر کند؛ تغییر قوانین پرداخت، تغییر دیتابیس یا تغییر API خارجی. چنین طراحی‌ای رعایت SRP را دشوار می‌کند.

۲. تقسیم مسئولیت‌ها

می‌توان کلاس را به اجزای متمرکزتر تقسیم کرد:

```
public class PaymentService {
    private final PaymentRepository repository;
    private final PaymentGateway gateway;

    public PaymentService(
            PaymentRepository repository,
            PaymentGateway gateway) {
        this.repository = repository;
        this.gateway = gateway;
    }

    public void pay(Payment payment) {
        // Coordinate the payment use case
        gateway.charge(payment);
        repository.save(payment);
    }
}
```

در این مثال، `PaymentService` جریان اجرای عملیات پرداخت را هماهنگ می‌کند؛ `PaymentGateway` ارتباط با ارائه‌دهنده پرداخت را انتزاع می‌کند و `PaymentRepository` مسئولیت ذخیره‌سازی را بر عهده دارد. جزئیات هر مسئولیت در پیاده‌سازی مربوط به خودش قرار می‌گیرد.

۳. مزایای SRP

- Maintainability: تغییر در یک مسئولیت، اثر کمتری بر بخش‌های دیگر دارد.
- Testability: هر کلاس را می‌توان با Mock کردن وابستگی‌هایش مستقل‌تر تست کرد.
- Reusability: اجزای متمرکز راحت‌تر در بخش‌های دیگر استفاده می‌شوند.
- Lower Coupling: وابستگی‌های ناخواسته کاهش می‌یابند.
- Team Productivity: توسعه‌دهندگان می‌توانند بخش‌های مختلف را با تداخل کمتر تغییر دهند.

۴. SRP به معنی ساختن کلاس برای هر متد نیست

یکی از اشتباهات رایج، افراط در خرد کردن کلاس‌هاست. اگر هر تغییر کوچک نیازمند تغییر چندین کلاس، Interface و Factory باشد، احتمالاً طراحی بیش از حد پیچیده شده است.

برای رعایت SRP باید:

- مسئولیت‌ها را بر اساس دلایل واقعی تغییر تفکیک کرد.
- از `Cohesion` بالا و `Coupling` پایین حمایت کرد.
- مرزهای ماژول‌ها را با توجه به نیازهای کسب‌وکار و معماری تعیین کرد.
- در صورت نبود دلیل کافی، از ایجاد abstractionهای غیرضروری خودداری کرد.

نتیجه: SRP یعنی هر کلاس یا ماژول حول یک مسئولیت منسجم طراحی شود و یک دلیل اصلی برای تغییر داشته باشد. رعایت آن نگه‌داری، تست‌پذیری و توسعه‌پذیری را بهتر می‌کند، بدون آنکه به خرد کردن افراطی کلاس‌ها منجر شود.
